## Composite-constraint design rule

Where parent IDs are globally primary-keyed today, a same-tenant relationship can be enforced by adding a unique key on `(college_id, id)` to the parent and a composite FK `(college_id, parent_id) → parent(college_id, id)` to the child. This is design guidance only; actual DDL must be rehearsed and validated against the real PostgreSQL version/schema.

## Required indexes and uniqueness review

Every tenant-filtered query should lead with `college_id` in the relevant index, validated with query plans. Global identity values such as login email stay globally unique. College-local identifiers (roll number, employee ID, subject code, section/class codes, counters) should become tenant-scoped only after duplicate analysis. Existing global constraints must not be relaxed until callers and identity semantics are updated.

No migration SQL is drafted or applied in this phase. Migration is **BLOCKED / NOT APPLIED** pending approved mapping and isolated PostgreSQL rehearsal.
