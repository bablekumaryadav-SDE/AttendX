## Proposed sequence and recovery

1. Obtain explicit approval for both password changes (A and B), the temporary cluster outage/single-user maintenance, secure replacement-file staging/activation (C–F), and the specific exact paths in the table below. Recheck process/data-directory/system-ID immediately before any future state change.
2. Generate two independent high-entropy replacement values from a cryptographic RNG in memory. Never emit them to output, reports, command arguments, clipboard, shell history, `.env`, or plaintext files. Do not derive from or compare with the old values.
3. Create the absent pending file initially empty, protect its DACL before writing encrypted content, and store the values using Windows PowerShell CurrentUser DPAPI. Use the current user SID Full Control only, no inheritance, and verify the ACL. Perform an in-memory encryption/decryption round trip using pass/fail comparisons without printing values. If any storage/round-trip check fails, stop before changing either PostgreSQL password.
4. Stop only the verified test postmaster under the approved maintenance window. Recheck the exact data directory and system ID. In one offline single-user transaction, set `password_encryption` to `scram-sha-256`, change `attendx_cluster_admin` and `attendx_test_role` to their separate new values, and commit. No role attributes, memberships, databases, or data rows change. Do not run `initdb` or alter `pg_hba.conf`.
5. If the offline transaction fails before commit, keep the original active DPAPI file unchanged, discard the unactivated candidate only under the approved cleanup scope, and stop. If commit status is uncertain or restart/authentication fails, do not restore or test the exposed old credentials. Preserve the staged encrypted candidate and cluster; after identity review, the recovery path is another separately approved offline reset to newly generated values.
6. Restart only this cluster on `127.0.0.1:55432`. A fresh authentication check (G) is not included in A–F and must wait for separate approval. Until G passes, do not retire the old encrypted file or claim successful credential recovery. After later G approval and successful new-credential checks, create the activation copy from the still-verified pending ciphertext, set/verify its restricted ACL, then atomically replace the canonical file while moving the old file to the exact retirement path. Keep the pending encrypted candidate until the canonical DPAPI round trip and authentication checks both pass. Only then retire the old file and temporary candidates. File deletion is not guaranteed secure erasure; database password replacement invalidates old values.
7. If activation/canonical-file verification fails, preserve the pending encrypted candidate and old retired ciphertext, do not write credentials to plaintext, and do not roll the database passwords back to the exposed values. Repair/reattempt activation from the already verified pending ciphertext under approval; if its DPAPI round trip fails, stop and repeat offline rotation with newly generated values after separate approval.

The existing cluster directory and system identifier remain the recovery anchor. A cold physical cluster copy before the catalog update may be useful, but it needs its own exact path, storage/ACL review, collision check, and explicit approval. The Phase 11 empty logical dump is not a physical cluster backup. No copy is authorized by this plan.
