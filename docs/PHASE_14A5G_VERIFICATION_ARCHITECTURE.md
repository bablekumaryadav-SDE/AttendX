# Phase 14A.5G — Rotation Verification Architecture

**Date:** 2026-11-09
**Scope:** Documentation and architecture review only. The current implementation and prior adversarial finding were read; no wrapper, PostgreSQL, credential, or DPAPI operation was run.
**Decision:** **REPLACE** the current injected-executor wrapper for any future operational use. Keep it only as a historical/mock verifier artifact, clearly labeled unsafe for rotation decisions. No replacement implementation is authorized or created here.
**Rotation status:** A–E remain **BLOCKED / NOT APPROVED**.

## Threat model and trust boundaries

The adversary/error model includes accidental or malicious executor behavior, stale or replayed output, wrong executable or data directory, process launch failure, SQL parse/execution error, transaction rollback, crash or timeout around commit, truncated pipes, secret-bearing error output/logs, and operator confusion between “process exited,” “SQL ran,” “transaction committed,” and “new password authenticates.”

Current wrapper `backend/scripts/phase14a5e_rotation_wrapper.py` accepts an arbitrary caller-provided `execute_once` object and trusts its returned `ExecutionResult`. It does not launch or identify a process. A no-op executor returning the fixed constant token is accepted as `ROTATION_COMMIT_VERIFIED`; the Phase 14A.5F review reproduced this. A constant token is replayable. Therefore neither the current wrapper nor its mock tests establish PostgreSQL execution, commit, or credential validity.

For a future design, the trusted component would have to own all of the following within one narrowly scoped implementation: exact executable selection and identity validation; exact D: cluster identity and database arguments; process creation without a shell; private input delivery; bounded stdout/stderr capture; timeout/cancellation and child reaping; output parsing; and one-shot/no-retry state handling. There must be no caller-supplied executor, result object, or success callback at the security boundary. This narrows the trust boundary but is **not sufficient by itself**: a child process handle and exit code prove only that a process was created/ended, not that SQL was processed or committed.

## Evidence claims must remain separate

| Claim | Evidence a future design would need | What it does not prove |
|---|---|---|
| Process launch | Trusted launcher records the directly created child handle/PID, executable identity, exact arguments/data directory, and wait result using OS process APIs. | SQL was read or processed; any transaction committed. |
| SQL processing | A response generated by the intended PostgreSQL server for the submitted command entry, bound to the fresh invocation and obtained from the directly captured child channel. | A transaction committed unless it reports/queries transaction status. Arbitrary stdout, a mock, and exit status are not sufficient. |
| Transaction commit | In the same command-entry transaction, perform both role changes and durable-within-transaction marker insertion; then query marker XID status after command entry completion and accept only `committed`. Evidence must be invocation-bound and come from the trusted child channel. | That the supplied password values are correct/usable for authentication, or that no secret leaked through logs/dumps. |
| SCRAM authentication | A separately approved fresh SCRAM connection using the new credential to the verified isolated loopback cluster, with independent server identity checks. | Safe rotation execution or absence of historical exposure. This remains the separate G gate. |

PostgreSQL 18 documents that `pg_xact_status(xid8)` can return `in progress`, `committed`, `aborted`, or `NULL` when status is no longer retained, and describes use after a disconnect during COMMIT. This makes it a candidate transaction-status primitive, not proof that a particular output byte sequence came from a particular invocation. See [PostgreSQL 18 system information functions, §9.27.2](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-PG-SNAPSHOT).

## Invocation binding and replay prevention

A future protocol should generate a fresh, high-entropy, non-secret invocation identifier inside the trusted launcher for each attempt. It should be included in the temporary marker data and in the expected response. The verifier must compare the response against the identifier created for that exact attempt; it must never accept a constant success string. The identifier is not a credential, but must still be handled as transient protocol data and not accepted from the caller.

This is a **design requirement, not a validated PostgreSQL 18 protocol**. PostgreSQL single-user mode prints query results in a form the manual calls more useful to developers than end users; the manual does not promise stable machine-readable output framing. The manual documents `-j` command-entry framing and that statements in an entry execute as one transaction, but does not define a stable nonce-bearing response format. See [PostgreSQL 18 `postgres`, Single-User Mode](https://www.postgresql.org/docs/18/app-postgres.html#APP-POSTGRES-SINGLE-USER).

Consequently, nonce binding would defeat accidental stale/replay acceptance only if a trusted launcher binds it to a newly created child and the server output can be parsed unambiguously. It does not stop an arbitrary injected executor that can inspect the command bytes and fabricate the corresponding nonce response; removing that injection boundary is mandatory. No production protocol is established until a future design is reviewed against the real documented interface and an explicitly approved isolated integration rehearsal.

## Secret handling and evidence retention

- Do not put credentials in process command-line arguments, environment variables, shell text, history, transcripts, temporary files, logs, report output, or exception messages.
- Password-bearing SQL bytes necessarily exist in memory for this proposed method. Their lifetime, copies, crash dumps, paging, and adapter behavior are not proven safe by Python `bytes` or object `repr` redaction.
- Do not retain raw stdout/stderr, SQL input, exception strings, password verifiers, or decrypted DPAPI payloads. A future report may retain only fixed outcome categories, timestamps, executable/data-directory identity metadata, child PID/exit classification, whether capture was complete, whether an invocation-bound committed marker matched, and explicit UNKNOWN/FAIL state. Even metadata needs reviewed access controls.
- PostgreSQL documentation warns that `ALTER ROLE ... PASSWORD` cleartext can be logged in client history/server logs and warns server logs may contain sensitive information. Logging parameters or an in-memory pipe alone are not a complete proof that secret-bearing content cannot enter OS-level diagnostic artifacts. See [PostgreSQL 18 `ALTER ROLE`](https://www.postgresql.org/docs/18/sql-alterrole.html) and [PostgreSQL 18 log-file maintenance](https://www.postgresql.org/docs/18/logfile-maintenance.html).
- No safe logging/capture profile is certified here. Any logging overrides, diagnostic dump policy, OS crash-report behavior, child stdio redirection and restricted log destination require independent review and should fail closed if uncertain.

## Failure states and no-retry rule

| Event | Required classification/action |
|---|---|
| Launcher fails before child creation | `NOT_LAUNCHED` only if the trusted launcher can establish no child was created and no input was delivered. Otherwise `UNKNOWN`. Do not retry automatically. |
| Child created but no command response | `UNKNOWN`; process existence/exit is not SQL evidence. Stop. |
| SQL error or transaction rollback | `NOT_COMMITTED` only with invocation-bound evidence that the marker XID is aborted/absent and no unexpected second command entry could commit changes. Otherwise `UNKNOWN`. Never infer from exit code alone. |
| Committed marker returned completely and matches this invocation | Candidate `COMMIT_CONFIRMED` only after independent review validates provenance, parser, SQL framing and the actual PostgreSQL interface. This architecture phase does not establish that condition. |
| Crash, timeout, truncated output, malformed/duplicate/missing/mismatched response, stderr anomaly, unexpected output, wait/capture failure | `UNKNOWN`; never retry the password-changing transaction. Preserve state and require a separately approved recovery plan that assumes either partial/complete state. |
| SCRAM authentication fails or is not performed | Commit and authentication remain separate claims. G is not implied; do not try old compromised credentials. |

An ambiguous outcome must never trigger automatic re-execution: a transaction may have committed even if the response was lost. Any recovery action requires a fresh, separately approved plan.

## Adversarial test plan and limits

| Scenario | Unit-testable? | Separate isolated-cluster integration required? |
|---|---|---|
| No-op executor returns fixed success token | Yes; corrected architecture must not expose an injectable executor. A protocol-level fake must be rejected. | No, to prove this architectural property. |
| Replay previous invocation response | Yes; fresh invocation binding must reject old evidence. | Real integration still needed to validate how the server emits the fresh identifier. |
| Token for another invocation | Yes; strict identifier mismatch must fail closed. | Yes, for actual server response framing. |
| Duplicate, malformed, missing evidence | Yes; parser boundary cases. | Integration validates the parser against actual version-specific output. |
| Process never launched | Unit tests can inject launcher failure and assert no success; process creation itself needs a controlled launcher integration test. | Yes, to verify OS child-handle/wait implementation, without PostgreSQL side effects. |
| Process launched but SQL not processed | Mocks can prove no response means no success, not what PostgreSQL processed. | Yes, on a disposable isolated cluster with a harmless approved fixture/probe. |
| SQL error and rollback | Parser/state-machine unit tests can cover supplied evidence. | Yes, to validate single-user framing and transaction behavior. |
| Commit succeeded but output truncated | Unit tests must return UNKNOWN and assert no retry. | Yes, to exercise child termination/capture behavior; no credential-change action absent separate approval. |
| Crash/timeout with unknown commit outcome | Unit tests cover state classification/no retry. | Yes, only a separately approved failure-injection rehearsal can validate real process timing. |
| Synthetic password text in raw output | Unit tests cover no-return/no-print behavior with dummy values. | Integration is needed to inspect logging/capture paths; must not use actual credentials in test output. |
| Unexpected stderr/exception with synthetic SQL/password | Unit tests cover fixed UNKNOWN and redacted outward result. | Integration validates real process adapter and logging surfaces. |
| Automatic retry after ambiguity | Unit tests assert exactly one launch attempt and terminal UNKNOWN. | Integration can validate launcher does not respawn/retry after timeout/crash. |

Unit tests cannot prove PostgreSQL parser behavior, process identity, SQL receipt, transaction commit, SCRAM authentication, or absence of operating-system-level secret artifacts. Those claims need appropriately authorized isolated integration checks and separate approvals. This Phase 14A.5G authorizes none.

## Decision and blockers

**RECOMMENDATION: REPLACE.** Do not extend the current arbitrary-executor wrapper into an operational tool. Preserve it and its tests as historical mock evidence, but deprecate `COMMIT_VERIFIED` as a trustworthy rotation result. A future replacement must own launch/capture inside the trusted boundary, bind evidence to a fresh invocation, and prove through official-interface review and a separately approved isolated integration rehearsal that output provenance and secret containment are real.

Unresolved: stable machine-readable single-user output; provenance of nonce-bearing output; OS process identity and capture implementation; password leakage through server/OS diagnostics; crash/timeout behavior at commit; independently reviewed integration protocol. Until addressed and independently reviewed, A–E remain **BLOCKED / NOT APPROVED**. G, canonical DPAPI activation/retirement, and Phase 14A database operations A–D remain separate and unapproved.

## Actions not taken

No PostgreSQL process, SQL, port, service, credential, DPAPI file, database, backup, restore, migration, `.env`, or application configuration was accessed or operated. No wrapper or credential-related test was run. No credential-rotation approval was requested.

## Phase 14A.5H research addendum (2026-11-09)

Official PostgreSQL 18 documentation identifies authenticated SQL through psql `\\password` and transaction-state reconciliation with `pg_xact_status(xid8)` as a stronger **conditional candidate** than parsing single-user output. It depends on a valid uncompromised administrator login, a known XID, a follow-up authenticated connection to the verified same cluster, and validation of the exact two-role prompt/transaction workflow. Those prerequisites are not established here. The design conclusion is **INCONCLUSIVE**; A–E remain **BLOCKED / NOT APPROVED**. See `PHASE_14A5H_ALTERNATIVE_VERIFICATION_RESEARCH.md`.
