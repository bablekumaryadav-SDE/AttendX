# Student and Teacher Registration and Academic Progression

**Status date:** 2026-11-10
**Implementation status:** PARTIAL SOURCE IMPLEMENTATION
**Schema status:** DRAFT / NOT APPLIED
**Production readiness:** NOT CLAIMED

## What was implemented

The existing tenant Student and Teacher routers now expose narrowly scoped College Admin writes. Tenant context is resolved from the authenticated account's active `CollegeMembership` and active College on each request. The query parameter `college_id` is only a selector and cannot grant access. The global `User.role` does not authorize these operations. Legacy student, teacher, attendance, class and assignment routers remain behind the existing default-deny dependency.

### Enabled Student operations

| Method and path | Behavior | Authorization and tenant checks |
|---|---|---|
| `GET /students/` | List College-owned Students; supports name, email, Student ID, enrollment and roll search, active state, course, department, admission year, current year, semester and section filters | Active `college_admin` membership; every query filters `Student.college_id` from resolved context; NULL ownership excluded |
| `POST /students/` | Create Student profile, generated Student code, inactive account, pending Student membership, optional guardian record, optional same-College class assignment and initial academic snapshot atomically | Active `college_admin` membership; supplied College selector must match membership; client cannot supply College, role, account ID, Student ID or password |
| `GET /students/{student_id}` | Read the scoped Student profile and linked guardian contact fields | Active `college_admin` membership; foreign, NULL-owned and missing IDs use the shared sanitized 404 |
| `GET /students/{student_id}/academic-history` | Read same-College academic snapshots | Active `college_admin` membership and scoped Student check |
| `POST /students/{student_id}/promotions` | Explicitly change current academic year, semester and section; optionally change the active class assignment; append a history snapshot with reason | Active `college_admin` membership; Student and optional Class must belong to resolved College; admission year is preserved |

### Enabled Teacher operations

| Method and path | Behavior | Authorization and tenant checks |
|---|---|---|
| `GET /teachers/` | List minimal Teacher profiles | Existing active membership roles; College filter from resolved context; NULL ownership excluded |
| `GET /teachers/{teacher_id}` | Read minimal scoped Teacher profile | Existing active membership roles; foreign, NULL-owned and missing IDs use the shared sanitized 404 |
| `POST /teachers/` | Create Teacher profile, database-generated Teacher ID, inactive account, pending Teacher membership and optional class/subject assignments atomically | Active `college_admin` membership; every assignment Class and Subject is checked against resolved College; client cannot choose College, role, account ID or password |

No other write routes were enabled. Teacher profile edits/deactivation, Student profile edits, class/subject creation, assignment lifecycle changes, attendance writes, reports and notifications remain unavailable or default-denied. The OpenAPI and default-deny contract tests now enumerate the exact registration/progression operations.

## Data and account behavior

- Student fields added to ORM metadata include date of birth, gender, enrollment number, admission year/session, program duration, current academic year/semester, section, course, mobile and address. Admission year and current academic year are separate values. Calendar year changes do not promote Students.
- Student code is generated by the backend as `ATX-<UTC year>-<random unique suffix>` and is protected by the existing global unique Student-code key. The database primary key is not client-selectable.
- Teacher ID is the database-generated globally unique integer `teachers.id`; employee ID is separately supplied and constrained by the existing unique rule.
- Existing `StudentGuardian` storage was extended for father, mother and parent email; guardian name/mobile are nullable so partial family records can be retained. No parent login is created.
- New Student and Teacher `User` rows receive an ephemeral random password hash that is never returned or logged; the User is inactive and its CollegeMembership is pending. Therefore the person cannot log in yet. No invitation email, activation token, password setup, forgot-password or reset workflow was implemented. This is a saved pending registration, not an activated account.
- The Student history model stores initial admission and explicit progression snapshots with College, Student, optional Class, admission year, current year, semester, section, reason, actor and timestamp. Promotion uses a row lock where supported and commits the current state and history together.
- Optional Teacher assignments bind Teacher, Subject, Class and `college_id` using existing same-College composite FK metadata. Student Class assignment and academic history similarly bind parents to the same College.
- Existing global unique constraints for Student email/roll number, Teacher email/employee ID and User email are unchanged. This can reject a value reused across different Colleges; changing those legacy uniqueness semantics requires a separate schema/data review.
- Profile photos are not stored. Face enrollment, consent, template encryption, liveness/anti-spoof checks, revocation and face-required attendance are not implemented by this change. Existing Face routes were not enabled or altered. No face data is returned through the new Student responses.
- No automatic College, ownership backfill, membership activation, role promotion or historical academic inference is performed. Existing NULL ownership remains UNKNOWN and is still excluded from tenant reads.
